## User Scenarios & Testing *(mandatory)*

### User Story 1 - Dynamic Question Generation (Priority: P1)

A student begins an English or Math quiz and receives questions dynamically generated by an AI, ensuring fresh and varied content for each session.

**Why this priority**: This is the core functionality that replaces hardcoded questions, providing dynamic content and enabling a more engaging learning experience.

**Independent Test**: A student can start a quiz for a subject, receive and answer questions, and the questions are observably different across multiple quiz attempts for the same subject/difficulty.

**Acceptance Scenarios**:

1.  **Given** a student selects an English or Math quiz, **When** the quiz starts, **Then** new and relevant questions for the selected subject are displayed.
2.  **Given** a student completes a quiz, **When** they start a new quiz, **Then** a fresh set of questions is presented.

---

### User Story 2 - Personalized Question Adaptation (Priority: P2)

The system tracks a student's performance over time, adjusting the difficulty and type of questions presented in subsequent quizzes to match their learning progress.

**Why this priority**: This enhances the learning experience by providing tailored content, making the system more effective for individual student needs.

**Independent Test**: A student consistently answers questions of a certain type or difficulty correctly/incorrectly, and in a subsequent quiz, the question selection reflects an adaptation to that performance (e.g., more challenging questions or more practice on weak areas).

**Acceptance Scenarios**:

1.  **Given** a student consistently answers specific question types incorrectly, **When** they begin a new quiz, **Then** they receive more questions related to those difficult topics.
2.  **Given** a student consistently answers specific question types correctly, **When** they begin a new quiz, **Then** they receive more challenging questions or fewer questions on mastered topics.

---

### User Story 3 - Instant Explanatory Feedback (Priority: P1)

After a student answers a question, they immediately receive an explanation for the correct answer, helping them understand their mistakes and reinforce learning.

**Why this priority**: Immediate and clear feedback is crucial for effective learning and directly addresses a key requirement from the user description.

**Independent Test**: A student answers a question (correctly or incorrectly), and an explanation detailing the correct answer and reasoning is shown immediately.

**Acceptance Scenarios**:

1.  **Given** a student answers a question, **When** they submit their answer, **Then** an explanation of the correct answer is displayed.
2.  **Given** a student answers a question incorrectly, **When** they submit their answer, **Then** the explanation clearly outlines why their answer was wrong and why the correct answer is right.

---

### Edge Cases

- What happens if the AI fails to generate questions? System should display an error, implement a retry mechanism with exponential backoff, and gracefully degrade (e.g., offer to load a limited set of local questions, or inform the user to try again later).
- How does the system handle an empty or malformed prompt for question generation? System should use a default prompt or request clarification.
- What happens if the API key for the LLM is missing or invalid? System should log the error and notify the relevant party.
- How does the system handle a student repeatedly answering questions incorrectly, or getting stuck on a particular topic? System should adapt by re-explaining concepts, providing simpler questions, or suggesting external resources.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST dynamically generate English and Math quiz questions using a large language model (LLM).
- **FR-002**: The system MUST store and retrieve an API key for LLM access from an environment variable.
- **FR-003**: The system MUST maintain a history of each student's performance, including questions answered, correctness, and time taken.
- **FR-004**: The system MUST use a student's performance history to inform the generation of future questions, adapting difficulty and topic focus.
- **FR-005**: The system MUST provide an immediate explanation of the correct answer after a student submits their response.
- **FR-006**: The system MUST ensure the generated questions, correct answers, and explanations are relevant to the selected subject and difficulty band.
- **FR-007**: The system MUST handle cases where LLM question generation fails gracefully, including implementing retry mechanisms with exponential backoff and graceful degradation in cases of rate limits or prolonged latency.
- **FR-008**: The system MUST only support a single user type, "Student", with no additional distinct user roles.
- **FR-009**: The system MUST identify students using a simple local profile or guest mode (e.g., a unique ID generated on the device, or a simple nickname entry).
- **FR-010**: The system MUST retain student performance history data until actively deleted by the student.
- **FR-011**: The system MUST define explicit mappings for difficulty bands to grade ranges (e.g., Beginner = Grades 5-7, Intermediate = Grades 8-9, Advanced = Grade 10) to align with the Constitution's target audience.

## Architectural Overview

This section describes the key architectural components and their interactions, particularly focusing on the integration of the Large Language Model (LLM) for dynamic content generation and adaptive learning.

### Core Components

-   **User Interface (UI)**: Built with PyQt6, responsible for displaying questions, capturing user input, and presenting feedback.
-   **Data Service**: Manages interaction with the local SQLite database for storing student progress, performance history, and potentially a cache of generated questions/explanations.
-   **LLM Service**: A critical new component responsible for:
    -   Interfacing with the Gemini API to request dynamic questions, answers, and explanations based on subject, difficulty, and student performance context.
    -   Handling API key management (from environment variables).
    -   Implementing retry mechanisms and graceful degradation for LLM API failures.
-   **Adaptive Learning Service**: Utilizes student performance history to determine optimal question parameters (subject, difficulty, type) for the LLM Service.
-   **Validation Services (English/Math)**: Existing services, possibly enhanced, to validate student answers against the dynamically provided correct answers.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% of dynamically generated questions are relevant and grammatically correct for the specified subject and difficulty band.
- **SC-002**: Students receive an explanation for 100% of questions immediately after submission, with an average display time of under 1 second.
- **SC-003**: Student engagement (measured by quiz completion rate) increases by 20% compared to hardcoded question quizzes within one month of deployment.
- **SC-004**: The system successfully adapts question difficulty and topic focus for 80% of students who complete at least 5 quizzes.
